# Data Persistence Structure

> Part of the agent guide, moved out of `AGENTS.md` so that it is read when its area is touched, not loaded into every session. A section named in italics elsewhere (*Avatars*, *The look*, *Jira*…) is a file of this folder: the index in `AGENTS.md` says which.


The application uses a **per-team KV store** architecture to eliminate write contention. Each team is stored in its own KV record, so concurrent updates to different teams never conflict.

### KV Store Keys

| Key Pattern | Description |
|-------------|-------------|
| `team:{teamId}` | One record per team, contains full Team object + `_rev` for optimistic concurrency |
| `team-index` | Maps lowercase team names to team IDs for fast login lookups |
| `retro-meta` | Stores `resetTokens` and `orphanedFeedbacks` (non-team-specific data) |
| `session:{sessionId}` | Real-time session state (retro or health check) |
| `global-settings` | Admin settings (info message, admin email, notifications, AI config). Written only through `updateGlobalSettings` — one key at a time, under the row lock, after a strict read — and read through the lenient `loadGlobalSettings` (see *Key Design Principles*) |
| `jira-settings` | The deployment's Jira connection `{ enabled, baseUrl, allowSelfSignedCerts }`, written by the console. A key of its own, read strictly (see *Jira*); not in archives |
| `team-secret:{teamId}` | A team's sealed Jira token, `{ jira: { v, iv, tag, ct, baseUrl, connectedAs, deploymentType, version, setAt, refusedAt? } }`. Never on the team record, never sent to a client, not in archives (see *Jira*) |
| `team-auth:{teamId}` | The team's session epoch, `{ v: 1, sessionEpoch, revokedAt }` (decision D3b). Absent until the first password change (epoch `'0'`). Never on the team record, never sent to a client, not in archives (see *the session epoch* below) |

**Two things are SQL tables rather than KV records, and both for the same
reason: a restore rewrites the KV store wholesale.** `backups` holds the archives
themselves (imported files included, `type: 'imported'`); `security_events` (audit H45) holds the audit trail, which would be
worthless if a restore could erase it. Neither is in a backup archive — see
`__tests__/archiveContract.test.ts` for what the archive does and does not carry.

### Team Record Structure (`team:{teamId}`)
```json
{
  "id": "abc123",
  "name": "My Team",
  "passwordHash": "...",
  "_rev": 5,
  "_updatedAt": "2025-01-01T00:00:00.000Z",
  "members": [],
  "retrospectives": [],
  "healthChecks": [],
  "globalActions": [],
  "teamFeedbacks": []
}
```

**The password minimum lives in `utils/passwordPolicy.js` and nowhere else**
(audit H39). Eight characters — NIST SP 800-63B's floor, chosen over ASVS
2.1.1's twelve because this password is a *shared* secret typed by a dozen
people on phone keyboards, and because the login limiter, not the entropy, is
what actually bounds guessing (decision D18) — imported by the four server write paths
(`/api/team/create`, `/api/team/:teamId/password`,
`/api/password-reset/confirm`, `/api/super-admin/update-password`) **and** by
the React forms, so a screen cannot state a rule the route does not enforce. It
is `utils/` rather than `server/services/` precisely because it has consumers on
both sides — `utils/inviteLink.js` is the same pattern. Two rules when touching
it: **never call it from an authentication path** (a team whose password
predates the rule must keep logging in — refusing to verify would lock out the
whole existing user base), and **never call it from
`server/services/passwordMigration.js`** (it re-hashes the short plaintext a
legacy record already contains, so a minimum there would leave those records
unconvertible). Raising the number is a one-line change; the boundary tests are
written as `PASSWORD_MIN_LENGTH ± 1` and follow it.

`passwordHash` holds a scrypt hash (`scrypt$N$r$p$salt$hash`, hashed at rest via
`server/services/passwordHashing.js`). **A stored value that is not a scrypt
record does not authenticate** — `verifyPassword` has no branch comparing a
stored string against a submitted password, and the authentication path performs
no writes at all. The dual-verify fallback and the rehash-on-login upgrade that
covered records predating hashing were removed once production reported the
eager startup migration finding nothing left to convert. Converting a legacy
record is `server/services/passwordMigration.js`'s job alone: it runs at startup
**and after either restore route**, which is what stops a rollback to a
pre-hashing archive from leaving teams unable to log in. It reads only each
team's `id` and `passwordHash` (`dataStore.loadTeamPasswordHashes`, one
projection in SQL, never cached — the summary cache feeds the anonymous login
picker, and a hash there would be one forgotten field away from it; on
PostgreSQL a row jsonb refuses makes it read the rows one at a time in Node
instead of failing the pass), so Node parses no full record at boot, and its summary line counts only the records it
actually rewrote (an update declined because another pod hashed first answers
success too). Do not reintroduce a
plaintext compare in the auth path. `/api/team/restore-session`
never returns a password; restored sessions are token-only. Invite links embed a
signed, team-scoped **invite credential** derived on demand from
`/api/team/:teamId/invite-credential` and bound to the team record's
`inviteEpoch` counter (absent means `0`; every password rotation bumps it,
revoking all outstanding invite links). `inviteEpoch` is stripped from client
responses and protected against writes through `/api/team/:teamId/update`, like
`passwordHash`.

**The session epoch** (decision D3b) does for session tokens what `inviteEpoch`
does for invite links. Each team session token carries it as an additive
`sessionEpoch` claim (the `rg1` prefix and `v: 1` are unchanged, so a 41.0 pod
accepts this release's tokens — `__tests__/sessionTokenCompatibility.test.ts`
holds a frozen copy of its validator), and `server/services/sessionEpoch.js`
decides: a token carrying the claim is current only while it equals the team's
epoch; a token without it (from before this release, or from an older pod
during the rollout) is current unless a password change came after its issue
time (`iat < revokedAt`), which is why the deploy signs nobody out. Five rules:

- **A row of its own, `team-auth:{teamId}`, read in one statement**
  (`dataStore.loadTeamAuthState`: whether the record exists and the epoch, the
  record's value never read). On the team record, reading it would parse the
  whole history on every token-authenticated write — the 38.1 hot path — and
  `/update`, merges, archives and a stale tab could carry or roll it back.
- **Random, never a counter** (`newSessionEpoch`, 128 bits). A whole-store
  restore rolls `inviteEpoch` back; a counter taken down and up again repeats a
  value and revives the tokens minted under it.
- **Rotated in the password's own transaction** (`atomicTeamUpdate(…, {
  rotateSessionEpoch: true })`, team row then auth row): two concurrent changes
  end with one password and that change's epoch. The three password routes use
  it. A whole-store restore rotates (blindly, before *and* after writing the
  team, each best-effort) every team whose archived `passwordHash` differs from
  the current one, whose record could not be read, or that it brings back, and
  forgets the epochs of the teams it deletes; the single-team restore does the
  same for a team it recreates. `migrateLegacyPasswords` never rotates (the
  password does not change), nor does a merge (a new team id).
- **Read strictly.** A row that does not parse throws
  `TeamAuthRowCorruptError`: the routes answer 500, the socket denies and cuts
  (a query error during an outage, by contrast, is accepted on the token's
  signature and re-checked by the periodic sweep). A password change writes the
  row blindly, so it repairs it.
- **Deleted after the team record**, best-effort (`deleteTeamRecord`): before,
  it would reset a live team to epoch `'0'`. A boot sweep
  (`sweepOrphanedTeamAuthRows`) removes what a failed deletion leaves behind,
  one conditional `DELETE` per row (no team record, and the row older than ten
  minutes): it runs while other pods serve, and a check followed by a separate
  delete let a restore that recreated the team land in between, so the sweep
  removed the epoch the restore had just written.
`mergedFrom`, the provenance a super-admin merge writes on the team it creates
(see *Merging teams*), is server-only in the same way: stripped from every
client response and ignored by `/update`. So is `jiraClaims`, the Jira route's
record of the issues being created right now (see *Jira*), and
`jiraParentClaims`, its twin for the parent issues of `sessionParent` mode.
`jiraTarget`, where the team's issues go, is sent to clients but written by
`/jira/target` alone; `jiraParents`, each session's parent issue keyed by
`retro:<id>`, `healthcheck:<id>` or `backlog` (`{ key, createdAt,
subtaskTypeId? }` or `{ uncertainSince }`), is sent to clients but written by
`/jira/issues` alone. Neither is on a retro entry nor a `session:{id}` row: a
persist replaces the whole entry with a participant's blob, and a session row is
participant-writable.

`memberAvatars` maps each member id to that member's avatar choice,
`{ id: <avatar id> | null, at: <server ms> }`, written by `/member/avatar`
alone and ignored by `/update`. It is a top-level key, not a field of the
member row, because `/members` replaces the rows wholesale with whatever roster
a client cached: a stale tab would lose a value kept there. It is sent to
clients as stored and read through `memberAvatar` / `memberAvatarId`
(`utils/avatars.js`), as data (the route and the merge read the whole map
through `memberAvatarEntries` and the roster through `rosterIds`; a client
merges a pick's answer through `mergeMemberAvatars`): any holder of a team
credential can post anything. An entry whose `at` is not a date (`isAvatarTime`: whole
milliseconds that a number counts exactly) is no entry. A merge re-keys it through the member-id map (an entry one team
kept for an id that is off its roster and on the other team's is not carried
onto that other member; `mergedMemberAvatars`:
for a member the merge unifies, the primary's entry wins, a clear included —
a first "My initials" too, stored as an entry like a picture — and the
secondary's is used when the primary has none); a single-team restore keeps
the current map (`KEPT_FROM_CURRENT`); a whole-store restore puts the archive's
map back with the record. A session's participant copies carry `avatar` and
`avatarAt`, and the newer `at` wins everywhere (see *Avatars*).

`teamFeedbacks` is stored on the record and stripped from every team-side
answer (`sanitizeTeamForClient`): the Feedback Hub reads `/api/feedbacks/*`,
no client version read it from a team, and its inline images were the largest
part of the answer. The client `Team` type does not declare it, so no screen
can start reading data that never arrives.

### Key Design Principles
- **Per-team atomic updates**: `atomicTeamUpdate(teamId, updater)` only locks the specific team record, not all teams. A team's updates run **one at a time on each pod** (`server/services/keyedQueue.js`), and each one reads, runs the updater and writes **inside one transaction holding the row** (`SELECT … FOR UPDATE` on PostgreSQL, a synchronous transaction on SQLite): the record is parsed once, the updater runs exactly once, and a writer from another pod waits on the row lock instead of failing. It replaced a compare-and-swap retried five times, under which a whole retro writing at once let one writer win per round: measured on PostgreSQL, 9 to 10 of 16 simultaneous writers on a 1 MB team got `max_retries_exceeded`, a 500 the client only logs, and the Dashboard missed what they carried. Three rules: **an updater is synchronous** (it runs inside the transaction; every one is); **one that throws fails alone** (its transaction rolls back, the updates queued behind it run); and the queue is what keeps the lock cheap — without it, sixteen writers of one team hold sixteen pool connections waiting on one row. A pod from an older release still compare-and-swaps through `atomicTeamSave`, which takes the same lock and reads the revision written here, so a rolling update mixes both safely. `__tests__/teamWriteConcurrency.test.ts` holds the contract and runs on PostgreSQL when `TEST_DATABASE_URL` is set (the two-pod case is only meaningful there)
- **A write authenticated by a session token does not load the team** (`authenticateTeam(…, { needsTeam: false })`). The persist routes, the action, template, member and feedback writes only need the verdict, and the write reads the record itself; loading it first parsed the team's whole history once more on every persist of a live session. A valid token is checked against the team's auth row (`dataStore.loadTeamAuthState`: one statement answering whether the record exists and the team's session epoch, which reads no value of the record), so a deleted team still answers `401 team_not_found` and a token a password change revoked `401 session_revoked`; a password still loads the record to verify the hash. A test double of the data store needs `loadTeamAuthState` for that path — `__tests__/helpers/teamAuthStateDouble.ts` provides one that models rotation (a double answering `'0'` forever would keep every suite green while it stopped describing the server)
- **The client sends one save per session at a time** (`queueSessionSave` in `services/dataService.ts`). A save still waiting at the end of the persist queue is replaced by a newer save of the same session — each one carries the whole session, and typing a group or column title saves on every keystroke. A save that has started is never replaced, and anything else queued closes the window, so coalescing never moves a save past another write (an action recorded on a retro must not reach the server before the retro does)
- **Team summaries are cached per pod, and a projection never casts per column** (38.0). `loadTeamSummaries` — the login screen's `/api/team/list`, the console, the boot passes — needs a few fields that live inside each team's record, next to its whole history. On PostgreSQL each `(value::jsonb)->…` column is its own cast, so five projected columns parsed every record five times: **1.7 s for 40 teams holding 25 MB**, growing with every retro run (SQLite's JSON parse cache hid it in CI, at 50 ms). Each pod now keeps every team's projection keyed by a fingerprint that costs no parse — the row's byte length (`octet_length`, read from the row or TOAST header) and its version — and projects only the rows whose fingerprint moved, with **one** cast per row (`OFFSET 0` stops the planner from folding the subquery back into one cast per column). The version is `xmin` on PostgreSQL: it changes with every row version whoever writes it, a pod from an older release included, and owes nothing to a clock (an `updated_at` from `NOW()` is the transaction's *start* time and depends on the column's precision). On SQLite it is `updated_at`, read **only when `PRAGMA data_version` says another connection committed**: the column is stored after the record, so reading it walks every overflow page of the store. This pod's own writes (`kvSet`, `kvDelete`, `atomicTeamSave`) forget their entry, so between foreign writes the length alone is the whole fingerprint. Measured on that data: cold 230 ms, warm 1.5 ms on PostgreSQL. `loadTeamSummary` — one team, read by every socket join (the joiner's role) and by `/jira/status` — follows the same rules on **that one row**: it reads one fingerprint, never every team's (the list path's re-projection of every team written since the previous read would run on every join, while every client of a live retro rewrites its team), an empty value reads as no team as `kvGet` does, and on PostgreSQL concurrent reads of one team at one fingerprint share one projection, so a reconnect wave casts the record once rather than once per joiner. It never moves the SQLite `data_version` marker, which belongs to the whole-list read. The projection also counts each team's retrospectives for the console's Teams tab (`retrospectiveCount`: every entry of `retrospectives`, closed, in progress and open boards alike, the list the team's Dashboard shows). It is read from the same single cast, and handed out only under `withRetrospectiveCount`: `/api/super-admin/teams` asks for it, while the anonymous `/api/team/list` never does and picks its four fields by name (`__tests__/teamResponsePayload.test.ts`). **A count over a list is guarded by the list's type** (`CASE WHEN jsonb_typeof(j->'retrospectives') = 'array' THEN jsonb_array_length(j->'retrospectives') END`, `json_type` on SQLite). `jsonb_array_length` raises 22023 on a scalar, an object or a JSON null, which is not a refusal `isJsonbRefusal` falls back on, so one record whose `retrospectives` is not a list would fail every list read for every team: the login picker, renames, merges, restores and the console. An absent or malformed list reads 0. The console reads only the count, never `retrospectives` (its list carries no history), and a pod from an earlier release sends none, which the tab shows as Unknown and sorts last. **A cast can refuse a row Node reads.** `kv_store.value` is text written by Node, whose `JSON.stringify` writes a lone UTF-16 surrogate as the escape `\ud83d` and a NUL as `\u0000`; `JSON.parse` reads both back, `value::jsonb` refuses both (`22P02`, `22P05`), and one such row fails every statement that casts it — for every team when the statement casts all of them. So a read that must work on such a row falls back to Node on the error, never on `null`: the socket's role lookup reads the full record once the summary read throws (`loadRosterTeam` in `socketHandlers.js`; a summary answering `null` still means the team is gone), and `loadTeamPasswordHashes` reads the rows one at a time on those two SQLSTATEs (`server/services/jsonbRefusal.js`). Text that is cut before it is stored goes through `utils/textCut.js` (`cutCodeUnits`, `ticketQuote`), never `slice`/`substring`, which keep half an emoji — the action-context excerpt, feedback titles, descriptions and comments, and AI group titles all did. The list projections (`loadTeamSummaries`, `loadAllTeamFeedbacks`) still fail on such a row, as they have since 38.0 (the console's Live tab, a later reader of the summaries, falls back to one team at a time — see `active-sessions`): `k8s/README.md` → *A team record PostgreSQL's jsonb refuses* repairs it in SQL. Rules: write a new JSON projection with a single cast (`loadAllTeamFeedbacks` follows it); never write a `team:` row without going through those helpers, or the caches cannot forget it (every one calls `forgetTeamProjections`, which forgets the summary and the feedback entry); summaries are handed out as copies (a copy per roster row — `User` is flat — and a deep clone of the nested merge provenance). On the client, `dataService.listTeams` answers `null`, never `[]`, when the list could not be loaded, and the picker then says so with a retry: an empty list invites the user to create a team, and `/api/team/list` shares the per-IP read limiter with a whole office behind one address. `__tests__/teamSummaryCache.test.ts` holds the contract, and runs against a real PostgreSQL when `TEST_DATABASE_URL` is set — CI only has SQLite, which is exactly the engine that hid this
- **The feedback board is cached per pod by the same rule** (`loadAllTeamFeedbacks`, read by `/api/feedbacks/all` on every Feedback Hub open and action, and by the console's feedback tab; uncached it parsed every team row each time, 233 to 331 ms on PostgreSQL at 25 MB). Each team's id, name and feedbacks are kept under the summaries' fingerprint, projected with one cast per row whose fingerprint moved, and forgotten by every write of this pod. Four rules of its own: **the SQLite marker of another connection's commit is per cache** (`sqliteFeedbackDataVersionSeen`): shared, a summary read would mark the commit as seen and the next feedback read would judge on length alone, missing a same-length foreign edit such as a status `pending` → `resolved`; **the stamp and size of a projected entry come from the projection query's own row**, never the fingerprint read, so a write landing in between is re-projected next time; **the arrays are shared and deep-frozen** — callers build new objects and never edit them (both routes spread every feedback and sort a new array), and an edit throws instead of corrupting the next answer; **a 16 Mi-character budget** (`TEAM_FEEDBACK_CACHE_MAX_CHARS`, images ride inline) **is decided again at the end of every read**, in storage order, so no admission state outlives a read: a team that does not fit is answered but read from the database every time, with one warning per pod. The orphaned feedbacks still come from `retro-meta`, one row, and the board still sends every image (listing without them needs a rolling-update plan: older clients expect them in `/all`). `__tests__/teamFeedbackCache.test.ts` holds the contract on both engines (PostgreSQL with `TEST_DATABASE_URL`)
- **The Dashboard reuses a whole-team load once.** Login, creation, restore-session and an invite join each download the whole team, and the Dashboard used to fetch it again a moment later. Its entry calls `refreshFromServer({ maxAgeMs: DASHBOARD_REFRESH_MAX_AGE_MS })` (5 s, in `App.tsx`), which serves the first entry within that window from the load and consumes it; a refresh never stamps, so a return from a session always fetches. Keep the constant out of `dataService`: several App suites mock that module with a factory, and vitest throws on an export the factory does not define. A refresh also waits, at most 3 s (`REFRESH_PERSIST_WAIT_MS`), for the writes queued before it: the session exit queues the session's last save and enters the Dashboard in the same tick, and a refresh answered first replaced the cache with a team that lacked it. A write queued after the refresh started can still be dropped from the cache by its answer until the next refresh; the server always has it. `__tests__/dataServiceTeamRefresh.test.ts` and `__tests__/appDashboardRefresh.test.tsx` hold it
- **A sign-out is final for everything still on its way** (`App.tsx` → `signOut`: Logout, "Log in again", a participant's exit, and a participant with nothing to join). A save the Dashboard was awaiting, its refresh, or the effects of the commit that had just shown it can all finish after the sign-out, and each could open the team again with the view on LOGIN — App's empty shell until a reload — or write the removed saved session back. Four rules hold it. `signOut` calls `dataService.logout()`, which drops the team at once (`getTeam` answers nothing, and an answer arriving later is not kept: `keepAnsweredTeam`) but keeps the credentials until the writes queued before it have been sent — a participant's exit queues the session's last save and the roster just before signing out, so clearing them at once dropped those writes — unless a login replaced them meanwhile. App renders its main shell only for a team screen it can show (`teamScreen`); anything else is the login screen. A team on screen is replaced only through functional updates that never open one (`showLatestTeam`, the Dashboard refresh). And the effect saving the open session skips a commit rendered before the latest sign-out (`signOuts`), because React can run that commit's effects after the sign-out's handler. A participant who joins a team with no health check in progress and no retrospective at all is signed out with `login.notice.nothingToJoin` rather than left on an empty screen. `__tests__/appSignOut.test.tsx` forces each order, `__tests__/dataServiceLogout.test.ts` holds the dataService half
- **An invite link imports its team once** (`TeamLogin`'s `importedInvite` ref, keyed on the link object App sets once per link). App re-creates `onJoin`/`onLogin` on every render, and an effect that depends on them repeats its side effects: the invite effect re-imported the team on every App render (`/api/version` answering during the import is one), so every invitee downloaded the history at least twice, and each refused import of a stale link was one more `401` for `loginLimiter`. The effect reads the latest callbacks through refs. A refused import is never retried behind the user's back, and **a reload cannot retry it**: App removes `?join=` from the address as soon as it reads the link (and drops the stored session), so a reload shows the team list and the invitee would need the mail or the QR code again. The error screen therefore offers **Try again** (one import per click, the button kept on screen and marked busy while it runs, focus moved to the join screen when it lands there) and a way back to the team list. `dataService.importTeam` says whether a retry can help: a link the route refuses (400, 401, 403) is an invalid link, the login limiter's 429 says to wait, no answer at all says the server could not be reached (never the browser's raw "Failed to fetch"), and anything else, a 5xx or a gateway during a rolling update, says to try again in a moment. `__tests__/teamLoginInviteImport.test.tsx` and `__tests__/dataServiceInviteImport.test.ts` hold it, and `e2e-prod/static-delivery.spec.ts` counts one `POST /api/team/login` per link in the built app
- **`global-settings` is written one key at a time, under the row lock, never by a load-then-save.** The row holds independent settings with independent writers (the info banner, the admin email, the new-team switch, the AI configuration; `healAdminEmail` at boot and after restores). They used to load the row, change one key and save the whole blob, and `loadGlobalSettings` answers `{}` on a read error — so one database hiccup while saving the banner wrote `{ infoMessage }` over the row and erased the admin email, the switch and the whole AI configuration, while the route answered success; and two saves on two pods lost each other's change. Every writer now goes through `dataStore.updateGlobalSettings(updater)`: one transaction holding the row (on PostgreSQL an `INSERT … ON CONFLICT DO NOTHING` first, so two first writers lock the same row, then `SELECT … FOR UPDATE`; the synchronous transaction on SQLite), a **strict** read (a query error, a value that does not parse or is not one plain object throws, and nothing is written — the route answers `500 failed_to_save`), a synchronous updater that receives a copy and returns the next settings or null for "nothing to change", and the stored settings as the answer. Each caller spreads the current settings and sets its own key. `loadGlobalSettings` stays lenient **for readers** (the banner, the AI status, the notification mails degrade to "not configured"), and must never feed a write. There is no `saveGlobalSettings` any more, and `__tests__/globalSettingsUpdate.test.ts` → *global-settings writers* fails if any backend file calls one; the same suite holds the store contract on both engines (PostgreSQL when `TEST_DATABASE_URL` is set), and `__tests__/globalSettingsRoutes.test.ts` the five console routes against a real store whose read fails. Rolling-update residual: a pod from before this change still load-then-saves with the lenient read until it is replaced, so a console save it serves can still erase the other settings on a failed read, or overwrite a change another pod made meanwhile — leave the console's settings alone while such a rollout is in progress
- **Team index**: Used for login (name-to-ID lookup) and team creation (uniqueness check). The index and the `team:{teamId}` records are **two separate writes with no transaction between them**, so both handlers that touch the pair carry a compensating write. Creation claims the index entry *before* saving the record and **releases the claim if the record write fails** — keyed on its own team id, so a concurrent creation that legitimately won the name is never evicted. Deletion clears the index entry **first** and **never restores it**: that order is what keeps the record — and therefore the ability to authenticate a retry — alive when the second write fails, and the missing rollback is deliberate. Restoring the mapping after a failed `deleteTeamRecord` recreates the very state this ordering prevents as soon as two deletions overlap (A clears the entry and fails; B sees no entry, deletes the record, succeeds; A restores a mapping to a record that is gone). No re-check closes that, because the record can vanish between the check and the write, so the rule is structural: **a deletion only ever narrows the index.** Deletion clears **every** key mapping to the team, not the first match — a rename in flight legitimately holds two. **Renaming follows the same rule** (`/api/team/:teamId/update` and `/api/super-admin/rename-team`, both through `server/services/teamNameIndex.js`): it *claims* the new key while keeping the old one, writes the record, and only then releases **every key the team held at claim time** — the old name plus any alias a previously lost release left behind, which releasing the old name alone would have left claimed for good. That set is captured *before* the claim, so a key claimed by a concurrent rename of the same team is never in it and two overlapping renames cannot delete each other's claim. No failure path ever has to restore a mapping, and a claim that finds the name already the team's own is not released on failure, because this request did not add it. The rollback it replaces did restore one, and that is what made it dangerous — for the width of the record write the old name was free, so a concurrent creation could take it and then be silently evicted by the rollback (its record survives, its name resolves to the other team, nothing in the UI reaches the state), and a deletion landing in the same window left the restored name pointing at a record that was gone. A compensating write may only ever remove a mapping **it added itself**. The state all these guards exist to prevent is a name that resolves to no record: `/api/team/create` answers `409 team_name_exists` from the index alone, `/api/team/login` answers `401 team_not_found`, `/api/team/list` scans records so the team is invisible, and nothing in the UI can free the name again. Team names are trimmed on creation, on rename and in the availability check, so all three agree on what a name resolves to
- **orphanedFeedbacks**: `TeamFeedback` objects preserved from deleted teams. When a team is deleted, its feedbacks are moved to `retro-meta` so bug reports and feature requests are never lost. All feedback endpoints check both `team.teamFeedbacks` and `orphanedFeedbacks`. The move is an **upsert by feedback id**, because a deletion that fails on a later step is meant to be retried: an unconditional push duplicated every feedback (`/api/feedbacks/all` concatenates team and orphaned feedbacks, so the duplicates show on the board, and every writer resolves an orphan by first match, so only one copy of the pair would ever be updated again), while merely *skipping* an already-preserved id lost data the other way. Every feedback writer — the comment routes and the super-admin status/comment/delete routes — looks in the team record first and only falls back to `orphanedFeedbacks`, so a change made between a failed attempt and its retry lands on the **live** copy; the retry must therefore replace the stale snapshot, not keep it.
- **Automatic migration**: On startup, the server checks for legacy `retro-data` single-blob format and automatically migrates to per-team storage
- **Backup/restore**: An archive is built **team by team through gzip** (`server/services/backupArchive.js` → `buildBackupArchive`, on `stream/promises.pipeline`), by every backup, every snapshot and the `/api/super-admin/backup` download alike (`backupService.buildArchive`): the largest single `JSON.stringify` is one team, zlib runs asynchronously, and only the compressed bytes accumulate — where it used to hold the store parsed, stringified whole and gzipped synchronously, three copies at once and a second-long event-loop freeze. The bytes are those of `JSON.stringify(await loadPersistedData())` for the same clock (compact; the download is compact too now, the same bytes a backup row holds), so pods of every release read a new archive and the reverse; `__tests__/backupArchiveStream.test.ts` pins the equality, a bound on the largest stringify, both directions of compatibility and, on PostgreSQL, the one-snapshot read. `loadPersistedData` itself has no production caller left: it is the reference representation the tests compare with, built on the same readers. A readable team a whole-store restore would refuse (no id or name, or an id another record holds) is archived anyway — refusing would take away the single-team restore of every other team — with one warning per backup naming it by id or position, never by content. `savePersistedData()` decomposes an archive back into the store. **A backup that cannot read every team record fails** — and so does one whose `retro-meta` is present but malformed: the archive readers (`dataStore.iterateArchiveTeams`, `readArchiveMeta`) throw `BACKUP_READ_FAILED` naming the key (never its content), and `loadPersistedData` throws instead of answering `{ teams: [] }`. That used to store an empty archive as a success, and since retention runs only after a stored backup, each failed automatic run purged one good backup. Now `createBackup` answers `null` (`createBackupOutcome` says `'failed'` apart from `'in_progress'`), so every snapshot fails too: both restores and the single-team restore answer `503 pre_restore_snapshot_failed`, console deletion `503 pre_delete_snapshot_failed`, the checkpoint `500 create_failed` (it answered `409` for any failure), the download `500 backup_failed`, and a failed automatic backup runs no retention, so the last good ones are kept. That lasts until the row is repaired or deleted by hand (`k8s/README.md` → *A backup that cannot read a team fails*, which says what goes with a deletion: a team row's name-index entries unless a backup brings the team straight back, and never `retro-meta` itself, which holds every deleted team's feedbacks). For a team row the login picker is already down in that state (an unparsable or empty row fails the summary projection; one that parses but is not an object gives a summary with no name, which fails the picker's sort or render); a malformed `retro-meta` breaks nothing visible — its readers see empty lists — so the failing backups are its only sign. The failure line says `Team record "team:<id>"` for a team row and `Record "retro-meta"` for the metadata. On PostgreSQL the teams are read inside one `REPEATABLE READ READ ONLY` transaction (one snapshot across teams, as the single statement before it gave, at the cost of one pooled connection for the read); on SQLite one row at a time. `retro-meta` is read after the teams on both, which covers feedbacks moving *into* it: a team deleting itself mid-backup orphans them before its row goes, so they show at worst twice (its copy and the orphaned one), never zero times (`__tests__/backupStrictReads.test.ts` pins the order). It does not cover feedbacks moving *out of* it — a single-team restore of a team deleted since the backup moves its orphans into a record the archive's team list, fixed when the build starts, does not hold — nor, on SQLite, a move between two teams (a console deletion of a merge source whose merged team sorts first): that one archive can miss them, while the restore's own snapshot and the next backup hold them (HARDENING_STATUS §3 H10). Teams come in key order on both engines. Restore is a **faithful replace**, not a merge: `savePersistedData(data, { mode: 'replace' })` upserts the archive's teams/index/meta and then makes the store match the archive exactly — it deletes `team:{id}` records absent from the archive (so a team deleted since the backup no longer lingers as a "ghost" in prefix scans / the super-admin dashboard) and clears all live `session:*` state (a backup never carries session blobs, and a stale session could let a client re-persist pre-restore state). `mode` defaults to `'merge'` (the historical additive behaviour) so non-restore callers are untouched. Both restore routes (`/api/super-admin/restore` and `/api/super-admin/backups/restore`) take a **protected** pre-restore snapshot first (survives retention purge — it may be the only copy of the pre-restore state; prune old ones manually) and **abort with `503 pre_restore_snapshot_failed` if that snapshot cannot be created** (never run the destructive replace with no recovery point); **every path that applies an archive checks it with one rule first**, `archiveShapeProblem` (`server/services/archiveShape.js`): an object, a `teams` array whose every entry has a non-empty string `id` and a string `name` with no id twice, and `resetTokens` / `orphanedFeedbacks` lists when present (extra top-level keys stay inert). `normalizePersistedData` turns a bad `teams` into `[]`, so a malformed upload would otherwise be coerced into a wipe-everything empty restore (an explicit `teams: []` still restores to empty), and a nameless team crashes the replace partway, after the earlier teams are written and before the index, the meta and the cleanup. The uploaded route checks before its snapshot (`400 invalid_backup_data` with `reason`) and answers its body limit as JSON; the import checks at write time; the stored-backup route checks the backup exists **from the metadata alone** before the gate and the snapshot (an unknown id used to leave an orphaned protected snapshot), then reads and checks the archive **after** the snapshot, deleting the snapshot on a refusal — never parse a whole-store archive before the snapshot, which reads the whole store team by team and would hold the parsed archive across all of it. Imported rows (`type: 'imported'`) are never purged and survive every restore: `savePersistedData` never touches the `backups` table. Then, after the replace, they clear this pod's session cache and `io.serverSideEmit('sessions-invalidated')` so **every other pod drops its session cache too** (correct at `replicas:2`; single-pod deployments skip the broadcast), and finally re-run `migrateLegacyPasswords` over the restored records: an archive predating password hashing puts clear-text passwords back into a store the startup migration already cleaned, and the startup pass runs only at boot. The rehash never changes the restore's outcome — a restore that really happened must not be reported as failed. **Nor may the parsed archive still be reachable when that pass runs**: the passes read the store again (projections now, but the parsed archive is still the largest object a restore builds), and an async route's suspended frame keeps every local it declared, so both routes read, check and apply the archive in a helper of their own (`applyStoredArchive`, `applyUploadedArchive`) that answers only the outcome. `__tests__/restoreArchiveRetention.test.ts` observes it with `gc()` in a child `node --expose-gc`. Residual: a client actively connected to a live session at the instant of restore can re-persist its in-memory session once as a fresh row — bounded (a new session, never a ghost team) and expected during a global rollback, so run restores during low activity.
- **Rating a closed action is team-record-owned too, and it is the one place many clients write the same record.** Every other per-user value lives in the session blob behind the `_rev` CAS; `impactRatings` lives on the action, because the dashboard rollup reads the team record and a vote must outlive the session that collected it. Three rules follow. **`closedAt` is stamped only by the paths that actually close an action** (`dataService.toggleGlobalAction`, `updateGlobalAction`, and `/api/team/:teamId/action`) — never from a full-session persist, which carries no reliable closing moment; an action with no `closedAt` is never proposed for rating, which is what keeps the pre-feature backlog out. **A vote goes through the narrow `/action/impact` route**, never a whole-action write. **Both closed-action guards — `reconcileRetroActionState` (client) and its server mirror — preserve `closedAt`, `impactRatings` (union) and `impactDeferredBy`** on top of `done`, because all three are written through routes that do not advance the retro `_rev`, and all three are additive: a session blob never legitimately removes a vote, a closing date or a deferral. Which closed actions a retro asks about is derived, not stamped — an action is "already asked" when it appears in a previous retro's `closedActionsSnapshot`, so there is no moment a fast facilitator can skip past, and `impactDeferredBy` (set by "Rate later") is the only decision that needs storing. **`closedActionsSnapshot` is the list the round *displays*, not the list it *asks about*.** Those were the same thing until the deferral became a toggle, and every consumer that means "the actions we are waiting on answers for" now has to go through `isDeferredInRound` / `rateableRoundActions` in `closedActionsForRating.ts`. Reading `snapshot.length` instead is what made a round of 9 with 2 postponed report `7/9` forever with the green tick unreachable, and the numerator matters as much as the denominator: a participant who answered before the deferral otherwise read `7/7` while someone who had not read `5/7`. **"Rate later" is a toggle and the row stays on screen while it is on** — removing it was the obvious implementation and the wrong one, because the only control that could bring a row back ("Rate now") lives on the *open* actions list, which no longer holds a closed action, so a mis-click cost the round that action with no undo anywhere in the session. Deferring never discards the votes already cast either: they are the participants' answers, and un-deferring has to put the row back as it was. The lag is structural: `selectClosedActionsForRating` excludes anything that was in this session's `openActionsSnapshot`, so an action ticked off right now belongs to the *next* retro's round unless the facilitator explicitly pulls it in with "Rate now"
- **Closing an action is team-record-owned**: An action is closed/re-opened (`done` toggled) through the granular action endpoints (`toggleGlobalAction`, i.e. `/api/team/:teamId/action`), which update the team record first — from the Dashboard **and** from inside a session (`OpenActionsPhase` and `ReviewPhase` both toggle through them, for carried-over *and* newly created actions). A full retro-session persist (`dataService.updateSession` → `/retrospective`) therefore runs `reconcileRetroActionState`, which guards the single `done: true → false` transition: a stale full-session blob — an open Session whose React state predates a close, or a lagging client re-persisting a retro while browsing — can no longer silently re-open a closed action. A *legitimate* re-open still works because it goes through the granular endpoint (which sets the stored record open first, so the guard lets it through). `assigneeId`/`text` and proposal state are deliberately **not** reconciled: several session-only flows (accepting/editing a proposal in Discuss, assigning a ROTI follow-up in Close) legitimately set them through the session blob without a granular endpoint. The `/api/team/:teamId/retrospective/:retroId` server handler enforces the **same** closed-only guard (`/action` does not advance the retro `_rev`, so a full-retro persist from a client that never saw the close would otherwise clear the rev guard and re-open it), which also protects the multi-client case where the reverting client's own cache is stale.
